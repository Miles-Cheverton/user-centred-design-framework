# Add a use case

Follow the [shared skill rules](../README.md) and the [use-case guide](../../how-to/files/use-cases.md). A use case describes an interaction; it does not replace a user need or an end-to-end journey.

## Procedure

1. Start from the service interaction supplied or developed by people. Establish the actor or group, goal, trigger and whether it is current or proposed. If these are unclear, retain a Draft and state the gap; do not invent a flow from raw research.
2. Check existing UC records for the same goal and scope. Keep an existing ID for a revision; use a new ID for a materially different case.
3. Resolve relevant UG and UN IDs. Describe the main user/service steps in plain language, including non-digital actions and staff handoffs where they matter.
4. Record the team's meaningful alternative routes, failures and recovery, and intended outcome. Distinguish known behaviour from proposed or unresolved behaviour. Flag missing branches for human consideration; do not supply interpretations, policy rules or implementation details to make the flow appear complete.
5. Link available EV or FND support and save the case in use-cases.md when authorised. Reviewed requires an actual review; it does not mean a proposed flow has been implemented or proven successful.

## Result

Return the UC ID, goal, current/proposed distinction, related needs and unresolved branches. Preserve superseded cases and their replacement references.
