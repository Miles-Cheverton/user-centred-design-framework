# Record a design option

Follow the [shared skill rules](../README.md) and the relevant [proposal](../../how-to/files/design-proposals.md), [journey](../../how-to/files/user-journeys.md) or [prototype](../../how-to/files/prototypes.md) guide.

## Procedure

1. Identify the human-developed option or version to retain: one used in research, informing a consequential decision, shared for substantive review or handed over. Disposable sketches can remain in normal working tools; substantive learning the team draws from them still belongs in the project. A quick layout experiment needs no entry merely because it exists; a discarded approach that changes the team's understanding needs its human reasoning retained.
2. Find an existing proposal or version. Keep one ID for revisions of the same journey/prototype and add an exact retained version; competing alternatives may need separate IDs. Do not treat the highest version as automatically selected.
3. Record the proposal’s intended change and uncertainty. Put prototype status and relationships in its register; use its README for the question, available tasks, run instructions and limitations. Do not maintain duplicate status or backlink lists.
4. Open and identify the exact retained version where accessible. For a service model, retain its graphic and faithful text description. Check named stages and handoffs, and preserve which parts describe prescribed, observed or proposed states. For a prototype, retain exact source or approved original-tool links and useful exports, and compare the description with accessible interactions. A working link can show changed content. Flag discrepancies for people to resolve.
5. Preserve meaningful discarded options and link the decision explaining the choice. Use the team's findings to describe learning; do not analyse a prototype or raw research to supply a new conclusion, invent findings or declare a selected design live.

If the source is a Microsoft Whiteboard, keep its reference with the relevant journey or prototype rather than creating a tool-specific central folder. Identify the canonical working link and the retained snapshot or version supporting this record; a mutable link alone is not the historical design. Retain the team's explanation in the existing text description or analysis notes and disclose unreadable canvas content. Do not derive a finding from sticky-note groupings. Use [research-material handling](../record-project-item/SKILL.md#research-materials) for source registration when needed.

## Result

Return the proposal ID and exact journey/prototype versions retained, their purpose and relevant decision/evidence links. This skill records design knowledge; it does not build or deploy a service unless separately instructed.
