# Use cases

**Working file (via document tracker)** [use-cases.xlsx](../../document-tracker.xlsx)

## First capture

Use a UC ID and name the user’s goal. Select **Current experience** or **Proposed experience** and start with **Draft**.

| Field | What to enter |
|---|---|
| ID | Stable UC ID. |
| Use case | A short name for the goal, such as Rearrange a repair visit. |
| User group IDs | Exact UG IDs for the people taking part. |
| User need IDs | Exact UN IDs where related needs are established. |
| Represents | Current experience or Proposed experience. |
| Interaction | What starts the interaction, what needs to be in place, user and service steps, important alternatives or recovery routes, and the intended result. Cite EV or FND records for observed behaviour. Link a journey or prototype when it provides context. For a proposed experience going into delivery, link the relevant backlog item and acceptance criteria, and the released build or exact version and check results when available. Record evidence of current behaviour separately from the intended result. |
| Status | Draft, Reviewed or Superseded. Reviewed means the team checked the description. Check **Represents** before treating it as current behaviour. |

Use these links to connect the intended interaction to the team’s delivery and verification work. Check the applicable version or release before relying on a test result. Update the relevant user need’s **Scope and evidence** with the assessment and supporting references when the team has agreed it.

Keep significant earlier cases. For a superseded case, record exact replacement UC IDs in **Interaction** or flag a missing replacement.
