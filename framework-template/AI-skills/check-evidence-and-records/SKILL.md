## Choose the check

Identify the claim, decision or area of the project in scope. Confirm the working folder, read the complete records needed and state which underlying sources you could check. [AI guidance](../../ai-guidance.md)

| Check | Method |
|---|---|
| Claim, proposal or decision | Verify the source and the users, versions and circumstances it covers. Flag gaps and discrepancies for people to interpret. [Check a claim](../../how-to/evidence-and-interpretation.md#check-a-claim) |
| Professional practice or standard | Read the [guidance for experienced teams](../../ai-guidance.md#advise-an-experienced-team). Identify the applicable criterion and check the team's evidence for the version, users and channels in the claim. Cite both sources. Report what is supported, what conflicts and what still needs specialist evaluation. Reserve formal sign-off for the responsible people. |
| User need assessment | Check the team's fulfilment judgement against its scope and evidence. Check the linked delivery decision separately. Use the [fulfilment and totals rules](../../ai-guidance.md#assess-whether-needs-are-met). [User needs guide](../../how-to/files/user-needs.md) |
| Project integrity | Read the Starter version in the project README. Use the [document tracker](../../document-tracker.xlsx) and project config to check expected files and links. Check ownership, duplicate or malformed IDs, all populated rows (including orphan rows), structure and required fields for the stage and scope. Extra columns are not a defect. Verify information outside the table against the owning record ID. [Check and repair project records](../../how-to/record-conventions.md#check-and-repair-project-records) |

Put any duplicate ID alert near the top of an integrity report. Give the ID and every confirmed location so the team can find the affected rows. Say which registers you could check if coverage was partial. [How to check IDs and incomplete rows](../../how-to/record-conventions.md#check-for-duplicate-ids)

For a Withdrawn finding or observation, check for the permitted source citation and reason for withdrawal. If data was intentionally removed under approved research arrangements, check the retained permitted explanation. Do not recover removed material. [Trace withdrawn evidence](../../how-to/record-conventions.md#trace-withdrawn-evidence) through direct and dependent claims. Check Answered research questions whose IDs appear in the affected findings and identify any remaining usable Reviewed findings. Report outstanding questions linked to the decision under review, including coverage gaps. Give IDs, current and recorded statuses, and usable support. Leave reassessment to the team.

For current assessments or verification, check what was actually tested and whether the relevant design version, release or scope changed. Identify any result that remains historical or needs review. For research coverage, check actual session roles and circumstances rather than inferring them from current participant groups.

Make a repair when the user authorises it and the correct change is established. Verify it after saving. Leave new findings, fulfilment judgements and decisions for the team.

## Help with a framework upgrade

Use the [upgrade steps](../../how-to/README.md#upgrade-an-existing-project) and the release's file list. Before making changes, identify the working project, its starting version, the target starter and a way to recover the files in scope. Resolve both folder locations before writing. Stage the ZIP and its extracted contents outside the working project. Never extract or bulk-copy a starter over the working project.

List the files you can replace, the ones that need merging and any conflicts the team needs to resolve. Use the old starter to identify team edits where available. Keep team-specific files, settings and records. Apply the listed changes only when authorised. If an earlier attempt partly succeeded, inspect the listed files first and resume from what remains.

Check a representative live record and its links after the update where one exists, including any mapped external record the team uses. For an empty or smaller adapted project, run the fictional quick test and verify the actual records, tracker links and controls in use. An intentionally unused register need not be populated or recreated. Use the [upgrade checks](../README.md#refresh-skills-after-an-upgrade) to compare the skill actually in use and both guidance files with the target starter. If a dependency is held back, keep using the previous matched set for saves. Call out anything still pointing at the old copy or any setup you could not verify. Set the **Starter version** in the project README only once the applicable upgrade checks pass.

## Report the result

Lead with the claim or decision affected. Cite what you verified and explain what is still open. If a source is needed to complete the requested check, inspect it within scope or say what access is missing. When asked for advice, identify the check most likely to change the decision and explain why. Report any repair and its verification. End with an **Unresolved** list if anything needs follow-up. Give the ID, location (workbook, sheet, row and field where available), issue and what is needed next.
