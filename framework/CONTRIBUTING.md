# Contributing

This starter is a draft. Improvements should make it easier for a team to do useful work and maintain dependable project knowledge.

The original framework is shared under [CC BY 4.0](LICENSE). Submit material you have the right to contribute on those terms, and identify any third-party material and its separate licence.

## Give useful feedback

Describe:

1. The task you were trying to complete.
2. The file, field or instruction involved.
3. What was unclear, missing or unnecessarily difficult.
4. The change you suggest and why it would help.

Use fictional or appropriately anonymised examples. Do not include participant details, recordings, restricted client material or secrets in public feedback.

## Propose a change

- Keep one clearly defined concept per file.
- Use established GDS terms where they exist. Identify our own naming and structural choices honestly.
- Prefer plain language and fields that support a real understanding, decision or action.
- Preserve stable record IDs and explain any change to references, fields or allowed values.
- Keep the data file, its how-to guide, worked example and any related prompt consistent.
- Keep the relationship table in the record-conventions guide consistent with reference fields. Confirm that linked IDs exist, versions resolve and replacement references do not form cycles.
- Cite the relevant primary guidance when changing a practice recommendation.
- Explain which existing users would need to change their files.

An Excel change should be checked by opening the saved workbook, exercising affected dropdowns and confirming that the main table and text remain usable. A Markdown change should be checked for understandable instructions and working relative links. Avoid adding administration solely to satisfy a generic checklist.

## Versioning

Use the changelog to explain changes in ordinary language:

- **Added:** a new capability or record.
- **Changed:** a revised meaning, field or workflow.
- **Fixed:** an error or misleading instruction.
- **Migration:** any action needed by existing users.

Do not silently change the meaning of an existing ID or field. A template update does not automatically alter a team’s live project records; describe the relevant changes so the team can adopt them deliberately.

## Review

A reviewer should be able to understand the reason for the change, inspect a practical example and assess its effect on related records. No contribution should claim GDS endorsement or universal legal applicability without a valid basis.

For changes affecting AI interpretation, use [the AI-usability evaluation](ai-usability/README.md). Keep its fictional project separate from the working template and record which tool and checks were actually used. Passing a small evaluation does not establish reliability across all models or future project data.
